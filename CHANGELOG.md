### Fixed

- The atomic write of `daemon.pid.json` no longer fails with `EPERM` on Windows: `writeJsonAtomic` waits out a rename refused while a reader holds the file open, with a budget of its own (`ATOMIC_WRITE_RETRY`) derived from the transient one of the lock instead of the eight attempts the lock spent.
- The end-of-run write of a spawned run is retried when Windows refuses the rename: `writeJsonAtomic` keeps the filesystem code in `cause`, and the retry in `src/spawn-process.js` looked only at `error.code`, so the first refusal ended the run unwritten and a failing client never reached `failed`. The retry now reads the code from `cause`, and the spawn tests derive their deadline from the exported retry budget instead of a flat 2 s.
- `withLock` treats a mkdir refused by Windows with EPERM, EBUSY or EACCES as a lost attempt instead of a fatal error: the contender tries again until its own timeout, and the timeout message now names the last refusal code (`last refusal: EPERM`), so a lock folder another process is taking or removing no longer ends the run with a raw code.
- A lock queue can no longer report a lock that nobody can take. The release in `withLock` now waits out EPERM/EBUSY like every other call of the lifecycle: it removes the owner file the holder has just written and closed, the file Windows and the antivirus behind it refuse to delete while they hold a handle, and a refusal there ended the bump *and* left the folder behind holding the owner of a process that was now gone and younger than `staleMs` — longer than every caller's timeout — so every contender behind it reported `Lock … is held by pid N … after 10000 ms`. A release that answers ENOTEMPTY (the folder was emptied but a contender wrote an entry back before the `rmdir`) or ENOENT (another contender removed it first) is a release, not a failure: the entry that answered is the only evidence every waiter of that folder reads, so retrying would take a lock from a live owner, and it is left alone. A refusal of the rename that moves a dead owner's claim out is likewise given up as one attempt instead of thrown out of `acquireLock`, so a takeover outlives a busy disk instead of ending the run on a raw code.
- The wait the state tests give a contender (`BUMP_WAIT_MS`) is sized from the retry budget a bump can spend times the widest queue instead of being a flat 10 s: with `owner` and `release` each refused for the whole budget one bump costs ~580 ms, and twenty queued contenders cannot fit that in ten seconds, which is how a queue of live contenders reported a lock "held by pid N" while every one of them was working and releasing.
- A stale lock takeover can no longer leave a folder nobody can claim: while it holds the dead owner's claim and has not written its own, the folder has no owner file at all, and the rename that moved the claim out refreshes the mtime that `claimFolder` judges an owner-less folder by, so any failure in that window — a claim read Windows refuses, a restore rename it still refuses, the removal of the claim — left a folder that stayed unclaimable for `staleMs`, longer than every caller's timeout, and every other process on the root then failed with `Lock … is held by an unknown process`. The owner write now waits out EPERM/EBUSY as every other call does, every way out of that window puts the dead owner's evidence back (the claim is renamed home, or, when Windows still refuses to move it, its bytes are written back with the same exclusive create that made it a claim), and a refusal that outlives every retry restores the claim and lets the poll loop judge again instead of throwing out of `acquireLock`.
- `src/spawn-process.js` retries the read and the write that end a run while Windows answers EPERM/EBUSY, and `renameWithRetry` in `src/state.js` waits out those codes with a pause that grows instead of a flat 10 ms. The end of a run was written once: a refusal, however short, was reported on stderr and never written again, so the run file kept `status: live` and the run was never seen to finish.
- `src/daemon.js` takes its lock once instead of waiting 300 ms for it: `timeoutMs: 300` is a budget between attempts, not a bound on the wall clock, and the deadline is only read after two filesystem calls, so on a Windows disk a second daemon on the same root polled about a dozen times and refused after 2274 ms. A lock left behind by a crashed daemon is still taken over on that first try, since the takeover runs before the deadline is looked at.
- A stale lock takeover no longer acts on a verdict read before an earlier lock was replaced, so a lock that is fresh but has no `owner.json` yet is never moved aside, and an owner that loses its folder before the owner file lands takes the lock again instead of failing.
- The stale-lock takeover claims the folder in place, renaming the dead owner's `owner.json` out of it instead of moving the folder aside, so the window where the folder could not be given back — after which the displaced owner's release deleted the live lock of whoever had taken the path — no longer lets two children into the same section.
- `test/state.test.js` forks itself through `fileURLToPath(import.meta.url)`, since the path part of a URL is `/C:/...` on Windows and `fork` could not start the child from it, and a forked child keeps its stderr, so a rejection now carries the last 2 KB of what the child said instead of only "child exited with 1".
- `test/spawn-process.test.js`'s `until` keeps the last value and the last error a poll saw and names both in the timeout, so the two run-file tests that fail only on Windows report what the run file said or why it could not be read.
- `src/spawn-process.js` reports every failure of the run file it used to swallow: the first write, the read-back before the record on exit, a run file that is gone by then, and the write of the record, each one line `okit: run file <path>: <message>` on stderr; the first write still throws, as before.
- Three tests spelled an expected path as posix text while the code builds it with `node:path`, so they failed on Windows and nowhere else: `configRoot` is expected as `resolve('/tmp/somewhere')`, the systemd, cron and launchd plans in `test/autostart.test.js` compare against `join('/home/u', ...)` and the `rm -f`/`launchctl` lines built from it, and `test/cli.test.js` ends the written path with `join('systemd', 'user', 'okit-daemon.service')`.
- `test/adapter-claude-code.test.js` removes each temporary folder once: `root` pushed into both the roots and the temps list, so the cleanup ran two concurrent recursive removals over the same tree and Windows answered `EPERM` from `rmdir` on a folder the other one was still emptying. The list is deduplicated and the removal asks for retries, with a test that fails on every platform if a folder is listed twice.
- A forked child of `test/state.test.js` writes the code, the message and the stack of a failed bump with `writeSync` on stderr before it exits, and the parent names how many milliseconds the child lived, so the wider takeover race reports why it died instead of only "child exited with 1".
