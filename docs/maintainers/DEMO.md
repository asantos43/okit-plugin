## 1. Scope and history
- 2026-10-26: design, isolated engine and user entry complete. Paid execution refuses without measured usage and a proven cost ceiling.
This demonstration lets a Director read synthetic work, choose actors, run independent work together, ask for review and return rejected work for correction. Everything described as proposed or to do is unimplemented. The current `client-smoke --demo` narrates C1–C23; it does not implement this orchestration.
The existing quick offline checks and injected C1–C23 tests remain unchanged. C1–C23 executed through a real client are already paid checks, not offline checks. The demonstration currently runs only with supplied test helpers, without a client, network or quota; paid execution remains unavailable.

## 2. Disposable scenario
Implemented in step 2: `src/smoke/demo/scenario.json` packages versioned JSON data, not executable code. It contains `version`, localized `title`/`body`, `kind`, internal `key`, `dependsOn`, `expectedSize`, `files`, `acceptance` and `fault` per demand. Internal keys never appear in user narration.
Acceptance entries are allowlisted data such as `{ "type": "fileEquals", "path": "welcome.txt", "text": "Welcome\n" }`; paths must be relative and contained. No shell commands or executable source in the scenario. Fixed scenario content and file checks are the same across clients and locales; only narration changes language.
| Work title | Size | Dependency | Observable acceptance |
| :- | :- | :- | :- |
| Welcome card | S | None | `welcome.txt` equals `Welcome\n`. |
| Opening hours | S | None | `hours.txt` equals `09:00-17:00\n`. |
| Visitor guide | M | Welcome card | `guide.txt` contains the supplied three sections and welcome text. |
| Ticket summary | M | None | `total.txt` equals `12\n`; planted fault is `11\n`. |
| Complete visit pack | L | All previous work | `pack.txt` contains the four approved outputs in scenario order. |
The first two demands have separate output directories and can overlap. The final pack reads approved artifacts only. S maps to `simple`, M to `normal`, L to `hard`; these are size labels, not model reasoning settings. Canonical classification input is shared: short bodies for S, three listed steps for M, six for L, without hint stems that override these rules. Step 2 tests the corpus through the actual `classify` tool.
Create a unique `mkdtemp` root under the operating system temporary directory; copy scenario data and seed files there, never run work in a user's project. Put HOME, client configuration, plugin state (`OKWORK_HOME`), inbox and actor working directories below that root. Import only approved effective configuration and read-only environment evidence; never copy credentials into reports. Use the installed plugin code read-only. Remove the owned scratch tree in `finally`, including after refusal or interruption; export reports to a caller-approved destination before removal. Never delete a path not created by this run.
The engine plants the fault itself after the first Ticket summary actor finishes, before review: overwrite its disposable `total.txt` with `11\n` and record that injection. Thus even an actor that immediately produces correct output cannot bypass the demonstration. Review reads exact bytes and must reject. On rework the injection is disabled; acceptance requires `12\n`. Report failure at the configured round limit, never force approval. Injection and review are implemented with deterministic test actors; real launches remain unavailable without cost enforcement and measured usage.

## 3. Director flow and briefings
The following calls name existing tools from `src/mcp/tools.js`. Step 2 composes their core functions in the injected engine; there is no existing MCP launch, briefing or critique tool.
1. Read one `src/env` snapshot through the existing environment path (`env_report`, `actors_list`, `limits_status`). Reuse it for preflight, profiles and capability evidence; do not redetect the environment in the demo. Explain: “I am checking which helpers are available.”
2. Validate the scenario, classification corpus, paths and dependencies offline. Show work titles, expected costs, quota evidence and ceilings; obtain explicit spending confirmation as described below. Explain: “This practice run uses your allowance.”
3. Bind the MCP context to the scratch state. Populate it with `inbox_add` (`title`, `body`, `kind`, `accept`, `appliesTo`); read via `inbox_list`. Keep generated identifiers only for internal correlation. Explain: “I have prepared five practice tasks.”
4. Call `classify` with `title`, canonical `body` and `kind` (its MCP schema does not accept `accept`). Retain its reason and map class to S/M/L. Explain: “The visitor guide is medium-sized.”
5. Call `profile_pick` with `client`, class in `effort` and the snapshot's quota `{source, remainingPct}`. This tool reads the scratch configuration: freeze its approved settings to match the snapshot. Check the selected model/effort against confirmed, launchable snapshot candidates and size coverage; a catalog entry alone is insufficient. Select a review-eligible critic separately. Explain: “I have chosen a helper for the guide.”
6. Schedule ready demands together when slots permit. Reserve cost atomically, then call `acquire_slot` with a unique attempt `runId` and `client`. A refused slot queues work without launching or charging; return its unused budget reservation. Respect global and per-client limits; never derive concurrency from quota percentages. Explain: “The card and opening hours can be done together.”
7. Generate an explicit Executor briefing and launch using supported native delegation or the adapter PROCESS bridge, not a fictitious MCP tool. Call `inbox_set_status` from pending to delegated once. In `finally`, call `release_slot` for every successfully acquired attempt, including exceptions, cancellation and failed launch. Review and rework launches acquire their own slots too.
8. After completion and the one-time fault injection, generate an explicit Critic briefing. Run deterministic acceptance first; model opinion cannot overrule failing bytes. Explain: “The ticket total is wrong. I am sending it back for correction.”
9. Rejected work stays internally delegated while a fresh attempt receives the failed criterion and artifacts. Repeat within `smoke.demoMaxReworkRounds`, rechecking quota, budget and slots. Only approved dependencies unlock further work. On final approval call `inbox_set_status` through delegated → criticised → consolidated; on exhaustion move to failed. Intermediate reviews live in the demo report, without reversing inbox transitions or inventing statuses. Explain: “The corrected total now passes.”
10. Stop, release slots, save the report and clean scratch state. If anything was skipped, explain: “PARTIAL: some practice tasks could not run.” Portuguese output uses “PARCIAL”.
Implemented briefing data (paid delivery remains unavailable): `role` (Executor or Critic), localized work title/goal, canonical demand, S/M/L and class/reason, actor `{client, model, effort}`, effective profile, scratch root and allowed output paths, approved dependency artifacts, acceptance entries, attempt/rework number, failed criteria, per-attempt time/turn/cost limits, remaining demand/total budget, cancellation signal and required result format. Human text has `Role: Executor` or `Role: Critic` (localized `Papel:` accepted by `src/roles.js`). Roles never follow from model choice.
Executor text: “Write the visit guide using the approved card. Work only in the practice folder. Include the three supplied sections. Return the files and what you checked.” Critic text: “Read the listed files, run the supplied checks and report which passed. Return failed checks for correction.” Keep user narration ordinary, with work titles instead of demand/order identifiers or tool names.

## 4. Quota, budgets and clean stop
Reuse effective `smoke.quotaFloorPct`, `smoke.quotaMaxAgeMinutes`, `smoke.quotaExpireMinutes`, `smoke.maxUsd`, `smoke.maxTurns`, `smoke.maxMinutes` and `smoke.checkTimeoutMs` from `config.json`/`src/profiles.js`. Never embed their current numeric values in the engine or scenario. Preflight uses the shared snapshot and existing `smokePreflight` policy; refresh stale evidence through the existing environment path, refuse unknown/expired/below-floor quota before real launches. A refreshed snapshot invalidates pending selection and spending confirmation.
New settings implemented and validated in `src/profiles.js`; the demo engine reads the resolved values and the entry points display them before confirmation:
| Variable | Default | Reader and rule |
| :- | :- | :- |
| `smoke.demoMaxReworkRounds` | `1` | Scheduler: nonnegative integer; counts corrections after the initial attempt per demand. Zero cannot complete the planted-fault demonstration. |
| `smoke.demoDemandMaxUsd` | `null` | Budget ledger: null resolves to `smoke.maxUsd / scenario.demands.length`; otherwise positive finite USD, capped by the total ceiling. Includes executor, critic and rework. |
| `smoke.demoRequireQuotaConfirmation` | `true` | CLI/MCP/skill confirmation handler: mandatory true for real mode; false is valid only with injected test actors. |
No new concurrency setting: existing slot limits are authoritative. Resolve `smoke.maxTurns: null` to the finite planned executor/critic call count including allowed rework; count every paid call against that run ceiling and retain each profile's own turn limit. Invalid settings refuse before spending. Configuration defaults are not hidden constants in the runner.
Before any paid call, show current quota/source/age, client, work titles, per-demand and total USD ceiling, possible correction rounds and time/turn limits. Ask for explicit consent: “This practice run uses your allowance, up to the displayed total. May I start?” A preview, entering demo mode or confirming settings is not consent to spend. No automatic headless approval; missing confirmation refuses without cost. MCP uses a preview followed by confirmation bound to the same plan, ceilings and snapshot; a changed plan requires confirmation again. This protocol is implemented by CLI and MCP through the same entry function.
Use one atomic ledger for parallel work. Before acquiring a slot, reserve a bounded maximum for that launch from both remaining budgets; other work cannot reserve the same money. Require an enforceable actor/driver cost ceiling covering native delegation or PROCESS plus usage evidence. If either is unavailable, skip paid launch with an explicit partial reason rather than promise a hard ceiling based on estimates. Unknown cost stays unknown; never report it as zero.
Charge actual executor/critic/rework use, return unused reservations, and account for in-flight reservations in the total. Every model call, including Director planning/narration if paid, is charged to the enclosing run and attributed to a demand or run overhead; fixed narration templates need no extra call. Estimated prices alone do not prove actual spending.
On budget, quota, turn, round or time exhaustion, stop scheduling, cancel in-flight work within its reserved caps, collect final usage, release every acquired slot, mark dependent/unstarted work skipped, export both reports and remove the scratch tree. Reaching a ceiling never counts as successful completion. Interruption uses the same cleanup; failed cancellations or unknown final usage make the result partial with the unresolved amount recorded.

Client-specific launch support does not change work, acceptance, failure injection or budget policy. Native role delivery is already implemented; the isolated scenario is implemented, while proof of real launches remains unavailable.
Client delivery: [adapters](../components/adapters.md).
Choose only actors that the current host can actually launch with the confirmed model/effort. Do not silently switch clients or treat a role-delivery fixture as launch evidence. If a client lacks launch capability, quota evidence, a critic, cost enforcement or a required model, mark affected demands skipped and the run PARTIAL/PARCIAL, stating why. A single available slot permits sequential completion, with a note that parallelism was unavailable; only an observed overlap proves the parallel demonstration.

## 6. Reports and narration
Implemented: plain UTF-8 text plus a JSON object from the same result. Text uses work titles, no demand/order identifiers. Example: “Ticket summary | M | helper: chosen client/model | profile: chosen effort | slot: acquired, released | approved | corrections: 1 | cost: measured USD”. If cost is unavailable, print “unknown”, not zero. A skipped launch produces its own “PARTIAL: Complete visit pack — helper unavailable” line (“PARCIAL” in Portuguese).
Implemented JSON contract: `{version, mode, client, status, reasons, limits, quotaEvidence, confirmed, demands, overheadUsd, costUsd, reservedUsd, events, cleanup}`. Run `status` is `pass`, `fail`, `partial` or `refused`; refusals precede spending, failures include unresolved acceptance, partial means any required work/evidence was skipped. Use exit 0 only for complete pass, 1 for fail/partial, 2 for preflight/confirmation refusal. These demo semantics are proposed, not a change to existing smoke exits.
Each demand has `{key, title, size, class, classificationReasons, actor, profile, slots, verdict, reworkRounds, costUsd, costKnown, attempts, skipReason}`. `actor` records client/model/effort; `profile` records the effective selection and origin; each slot records attempt, runId, acquisition and release evidence. `attempts` includes executor/critic role, start/end, reserved/actual cost, artifact paths, criterion results and injection evidence. Technical identifiers are allowed in JSON only. `costUsd: null` means unknown; injected mode reports zero with `mode: "test"`.
Record both observed spend and outstanding reservation, including cancelled attempts and run overhead; demand totals plus overhead must reconcile to run cost when known. Only count correction launches in `reworkRounds`, not the original attempt or critic calls. History/events display newest first with a monotonic sequence to break timestamp ties; the scenario dependency graph, not display order, schedules work. Narration covers preflight, confirmation, selection, slots, execution, review, correction, stop and cleanup in ordinary sentences. No stray blank lines in generated text.

## 7. Injected test mode and acceptance corpus
Implemented: inject `actor.run(briefing)` returning a promise of `{status, summary, artifacts, usage}`. The briefing is the section 3 object with a cancellation signal; `artifacts` is a list of `{path, content}` relative to the owned scratch root. The engine validates/writes them before fault injection and review. `status` is `completed`, `failed` or `cancelled`; usage contains measured `costUsd` and turns. Test actors are deterministic, return zero real cost and never spawn a model. Budget tests inject simulated priced usage/reservations clearly marked test-only, without quota consumption.
Inject `critic.review({briefing, result, artifacts, checks})` returning `{verdict, criteria, feedback, usage}`; verdict is `approved` or `rejected`, criteria contains each acceptance result and evidence. Artifact paths reference engine-validated files, and `checks` contains deterministic file-check results. Neither injected nor real critics may approve a failed check. A fake critic rejection/approval cannot replace testing the engine's actual byte check. Both interfaces honor cancellation; injected clock and completion barriers control ordering without timing-dependent sleeps.
Keep existing offline smoke and C1–C23 assertions. Add the following corpus in step 2 using `node --test`; it verifies behavior, not model wording:
- Classification  —  Five canonical demands yield S/S/M/M/L on every locale route.  —  Unexpected class or cyclic/missing dependency prevents launch.
- Parallel slots  —  Barriers prove two independent actors overlap with two free slots; one slot serializes; each acquired slot releases.  —  Launch at cap, double release or leaked slot after exception/cancellation.
- Planted fault  —  First review reads `11\n`, rejects; one correction writes `12\n`, next review approves.  —  Approval based on model prose while file is wrong; correction beyond configured rounds.
- Budget  —  Atomic reservations include parallel actors, critic, correction and overhead.  —  Total or demand ceiling exceeded; unavailable enforceable cap/cost evidence causes partial without launch.
- Isolation and consent  —  All work/state under the owned temporary root, cleanup after stop, no paid call before explicit confirmation.  —  Escaping paths, unsafe acceptance types, missing consent or unknown/expired/low quota.
- Report  —  Text/JSON agree, usage reconciles, newest event first, skipped work gets PARTIAL/PARCIAL.  —  Unknown cost represented as zero, skipped work marked pass, identifiers in user narration.

## 8. Steps 2–3 and acceptance
Step 2 API: import `runDemo` from `src/smoke/demo/index.js` with `{snapshot, actor, critic, clock, locale, signal}`. Only injected `mode: "test"` launches; simulated priced usage must supply `maxCostUsd` on each fake driver. The user entry binds consent to the displayed plan and allowance evidence. Paid driver capabilities remain unproven, so the entry refuses paid execution with exit code 2.
